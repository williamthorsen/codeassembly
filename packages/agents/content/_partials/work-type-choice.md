**Choosing a work type.** Whom a change affects decides its type, not the format of its files. Apply the descriptions in `{harness_home_dir}/skills/_data/work-types.json` to the change itself. Never infer a type from how earlier changes were typed, because many were typed wrongly.

**`fix` requires a defect that a consumer meets.** Two questions decide it, in order.

1. **Does a consumer meet the behavior that changed?** Where none does, the type is the one for that audience (`tests`, `tooling`, `ci`, `internal`), whatever the change repaired. A lint rule, a build script, and a test helper are not consumer-facing, so a repair to one is never `fix`. The same question settles a latent condition: Where no consumer could observe it, the change repairs no defect, and evidence that the condition pre-dated the change is not evidence that it was one.
2. **Did the effect differ from what its author intended?** Compare the intended effect with the actual one. That the code or the text was written deliberately does not settle it, because a deliberate rule can still produce an effect that its author did not intend. Where the effect diverged from the intent, the type is `fix`. Where it matched, and the change reflects a new decision about what the intent should be, the type is `feat`. Where intent and effect are both unchanged and only the construction differs, the type is `refactor`.

The test runs in both directions. `fix` is public tier, so typing an improvement `fix` publishes a "Bug fixes" entry telling every reader that something was broken, and typing a genuine defect `refactor` withholds a repair that a reader needs. A defect in consumer-facing behavior is `fix` whatever else the change does, and neither the branch's bulk nor the ticket's subject displaces it.

- **Repo-agnostic guidance is source code.** Skills, skill data, partials, subagent definitions, and rulebooks written for use in any repository take the type that the same change to source code would take. A wording correction is `fix` where the text failed to say what its author already intended, and `feat` where it states a new decision; the repair of a writing-rule violation is the former. A restructuring is `refactor` only when it leaves the text read by the agent unchanged, as extracting a partial does. A token cut that changes no behavior is `perf`.
- **Guidance on working in one repository is `ai`.** That repository's `AGENTS.md`, its repo-local skills, and its agent configuration take `ai`.
- **Guidance to agents is never `docs`.** `docs` is documentation for human readers, and a change confined to code comments is `docs`.
- **Content decides.** What guidance says decides whether it is repo-agnostic, not its file name, location, or format.
