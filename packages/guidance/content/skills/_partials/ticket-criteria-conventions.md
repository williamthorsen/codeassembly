**Test criterion convention:** When a ticket involves code changes to testable behavior, the acceptance criteria must include a test criterion (e.g., "New/modified behavior in this change is covered by tests"). Omit it when the change falls entirely within the carve-outs defined in the `testing-conventions` skill, or when the only tests it would compel are ones that fail that skill's bar for earning a place.

**Documentation criterion convention:** When a ticket involves changes that add, remove, or rename user-facing surface (CLI flags, commands, API endpoints, configuration keys, environment variables), the acceptance criteria must include corresponding updates to documentation, help text, and usage examples, including removal of references to anything that no longer exists.

**Umbrella criterion convention:** An umbrella ticket, whose children do the work, lists "Every child is closed" as an acceptance criterion alongside any requirement of its own, so that what completes it is stated rather than inferred. The criterion holds only when every planned piece has a child; therefore, when the split is decided, create a child for every planned piece, link it to the umbrella as a sub-issue, and link it to the pieces that must land before it through blocked-by relations. Specify the current piece fully, and keep each later piece short: its outcome, a few must-have criteria, and a note that it is refined when its work starts. Never leave a planned piece as an outline in the umbrella's body. To defer a planned piece, close its child as not planned.
